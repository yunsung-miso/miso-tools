# FE 챕터 월간 PR 리포트

챕터가 관리하는 repo들의 PR 데이터를 수집해 **생산성**(무엇을 얼마나 만들었나) · **기술부채**(부채가 해결되고 있나) · **리뷰**(리뷰가 제대로 일어나나) 세 축으로 챕터 상태를 진단한다.

이 리포트의 가치는 매달 **같은 정의로 같은 지표**를 뽑아 추세를 비교하는 데 있다. 그래서 집계 규칙은 사람이 매번 판단하지 않고 고정한다. 정의가 흔들리면 월간 비교가 무의미해진다.

산출물은 두 벌이다 — **백데이터 Markdown**과 **HTML 시각화 리포트**. 아래 규칙은 실제 리포트를 여러 달 다듬으며 합의된 것으로, **권고가 아니라 하네스다.** 지킬 수 없으면 자료를 만들지 말고 사용자에게 보고한다.

---

## 0. 범위 확정 — 가장 먼저

`AskUserQuestion`으로 확인한다 (이미 명시됐으면 생략).

- **대상 월** — 말하지 않았으면 직전 달로 가정하되 한 번 확인
- **대상 repo 목록** — 지난달 기준에서 편입·제외가 있는지. 있으면 §11
- **산출물 범위** — 백데이터 md와 HTML은 기본, 회의 어젠다(§6)는 선택

작업 디렉토리는 아카이브의 월 폴더(`~/Documents/fe-chapter-reports/YYYY-MM/`, 없으면 `outputs/pr-report-YYYY-MM/`)다. 모든 산출물을 여기 모은다.

## 1. 집계 규칙 — 불변 정의

사용자가 명시적으로 요청하지 않는 한 바꾸지 않는다. 새 패턴이 등장하면 보수적으로 확장한다. **보정 경위는 리포트에 쓰지 않고** 아카이브 `published-baselines.md`에 남긴다 (§7).

- **릴리즈/번들 병합 PR 제외** — 제목 패턴(`release/x.y.z to main`, `[x.y.z] merge to x.y.z` 등) **또는 브랜치**(head `release|bundle|codepush/` → base `main|master|release/|bundle/|codepush/`, `aggregate.is_merge_pr`). 제목만 보면 평범한 제목의 병합 PR이 개인 작업으로 샌다 (2026-09 실측 5건). 팀 전체 변경이 한 명에게 귀속되는 왜곡을 막는다
- **백포트 제외** — 제목 접미사 `(bundle/x.y.z)` · `(release/x.y.z)` · `(codepush/x.y.z)` · `(x.y.z)`. **고유 작업 = 집계 대상 − 백포트 − 봇**
- **봇 제외** — dependabot, gemini-code-assist, cursor, chatgpt-codex-connector, cubic-dev-ai, git-configurator, datadog-official, `app/*` 접두 전부. **`[bot]` 접미사가 없는 봇을 반드시 확인한다** — `copilot-pull-request-reviewer`를 사람으로 세면 사람 리뷰가 90% 과대 집계된다
- **작업유형 파싱** — `[Feature/TICKET]` 컨벤션의 대괄호 안쪽 첫 토큰. `[PRD-1234]`처럼 티켓만이면 "미표기", `feat:`·`ci:` 형태도 처리. **컨벤션이 바뀌면 파서를 먼저 고친다** — 안 고치면 대부분이 "기타"로 붕괴한다
- **의미 LOC** — lockfile · dist/build/generated · `__snapshots__` · .min. · .map · vendor/Pods · .pbxproj + 단일 파일 2,000줄 이상 데이터 파일 제외. **백포트 PR의 LOC는 개인 LOC에 넣지 않는다** — 원작업만 센다
- **스택 PR 중복 제거** — base가 `{type}/{TICKET}/…`인 PR을 (repo, 작성자, 티켓)으로 묶어 그룹 내 최대 diff로 근사. 원값과 함께 병기
- **리뷰 집계** — GitHub review 이벤트 기준, 셀프 리뷰 제외. Approve / Comment / Changes Requested 분리
- **1인 repo 예외** — `roster.json`의 `review_exempt_repos`(현재 design-tokens)는 "사람 리뷰 없이 머지"·"리뷰·테스트 없이 반영" 수치에서만 뺀다. **다른 지표에서는 빼지 않고, 문제로 짚지도 않고, "X를 뺀 값"이라고 적지도 않는다** (사용자 결정)
- **Give/Take·생산성×팀기여 산점도 금지** (2026-09 폐기) — 작성 PR이 많은 사람일수록 리뷰를 많이 해도 낮게 잡히는 구조다. 리뷰 기여는 **리뷰한 PR 수·CR 수 절대값**으로만 쓴다
- **배포 성과 = DORA 4종 + 테스트 동반률** (기능=티켓 단위, `scripts/delivery.py`·`compare.py` 정의 그대로) — 배포 빈도(사용자 반영 기능/월, native는 스토어·OTA 태그·웹은 main 머지) · 리드타임(첫 커밋→반영, 개발 구간/반영 대기 분리, 대기는 repo 단위만) · 변경 실패(첫 머지 후 14일 안 롤백·revert·hotfix 또는 bundle/·codepush/ 긴급 Bugfix·Fix) · 복구 시간 · 테스트 동반(jest·Apex Test·maestro·playwright·e2e-mock). 개인 전후 비교는 **같은 repo 기준**, 도입 전 기준 없는 repo는 현황 표로. 기간: AI 엔터프라이즈 플랜 도입(2026-05) 전 1~4월(native는 재구축기 1~3월을 빼고 4월만), 후 6월~, 도입 달 제외. 기능은 시작월 귀속, 부분월은 일수 가중
- **기술부채 = Refactor 유형 PR**로 한정. Chore(빌드·설정·의존성)는 부채 해결로 세지 않고 별도 표기
- **100파일 캡** — `--json files`는 PR당 100파일까지만 반환. 초과 PR은 `gh api repos/{org}/{repo}/pulls/{n}/files --paginate`로 재수집

## 2. 데이터 수집

**아카이브가 있으면 그걸 쓴다** — `~/Documents/fe-chapter-reports/`(README.md에 폴더 구성·링크). 과거 자료를 다시 찾지 말고 README·`published-baselines.md`·노션 백데이터 페이지를 먼저 읽는다. 사용자가 과거 자료를 주면 **수집 전에 먼저 읽는다.**

다개월 추이·DORA까지 뽑는 달은 월 폴더를 만들고 번들 스크립트를 복사해 돌린다 (상위 폴더에 `repos.txt`·`names.json`·`roster.json`):

```bash
cp ${CLAUDE_SKILL_DIR}/scripts/{fetch_months,fetch_extra,analyze,delivery,compare}.py 2026-MM/
python3 2026-MM/fetch_months.py 2026-MM        # 504면 재시도·범위 반분. 동시 실행 금지
python3 2026-MM/fetch_extra.py 2026-MM         # 첫 커밋 시각·머지 SHA (GraphQL 직접)
python3 2026-MM/analyze.py 2026-01 … 2026-MM   # 반드시 전 월 — extras.json을 덮어쓴다
NATIVE_GIT=<miso-native 클론> PNATIVE_GIT=<partner-native 클론> python3 2026-MM/delivery.py 2026-01 … 2026-MM
python3 2026-MM/compare.py
```

단월만 볼 때:

```bash
gh auth status   # 먼저 확인. 안 되면 gh auth login 안내

# repo 목록은 파일로 관리한다 (한 줄에 org/repo, # 주석 허용)
python3 ${CLAUDE_SKILL_DIR}/scripts/fetch_prs.py \
    --month YYYY-MM --repos-file repos.txt --out raw.json
python3 ${CLAUDE_SKILL_DIR}/scripts/aggregate.py \
    --in raw.json --out metrics.json --names names.json
```

`names.json`은 `{"github-id": "실명"}` 매핑이다 (§10). 없으면 아이디로 나온다.

페이지네이션과 리뷰 호출을 스크립트가 처리하므로 `gh api`를 직접 호출하지 않는다. 주간 청크로 나눠 수집한 뒤 단일콜과 합집합 대조한다. `aggregate.py`는 합계 검증을 내장하며 불일치 시 경고를 낸다 — 경고가 있으면 원인을 찾아 보고한다.

> **gh를 못 쓰는 경우**: raw 데이터(CSV/JSON)를 받으면 `${CLAUDE_SKILL_DIR}/references/data_schema.md` 포맷으로 변환해 진입한다. **완성된 .md 리포트만 있으면 집계를 건너뛰고 §4(시각화)부터 수행한다** — 이 경로가 실제로 가장 자주 쓰인다.

## 3. 백데이터 Markdown — 이게 SSOT다

**HTML보다 먼저 만든다.** 이후 모든 산출물의 수치는 이 파일에서 가져온다. 노션에 붙여넣을 수 있게 표준 마크다운만 쓴다(표·인용·코드펜스·헤딩, HTML 태그 금지).

구조 — `${CLAUDE_SKILL_DIR}/references/report_template.md`를 작업 디렉토리로 복사해 채운다:

1. **상단** — 기간 · 대상 repo · 필터링 원칙 · 이번 달 신규 보정(미보정 시 왜곡 크기 포함)
2. **repo 표** — 전체 PR / 집계 대상 / 고유 작업 / 머지율 / 백포트
3. **요약** + **전월 대비 변화** + **이번 달의 세 가지 사실**
4. **Part 1 생산성** — 개발자별 산출량 · 집중도 · repo별 분포 · 작업유형
5. **Part 2 기술부채** — 규모 · 어디서/누가 · **전수 내역** · 성격 분류 · 판정
6. **Part 3 리뷰** — 참여(절대값) · 리뷰 없이 머지 · 속도 분위수 · AI vs 사람 · 판정
7. **Part 4 배포 성과(DORA)** — 개인 전후(같은 repo) · 현황 · repo별 · 월별 추이 · 판정
8. **Part 5 종합** — 개발자별 한 줄 평 · 건전성 스코어카드 · 팀 차원 제안
9. **부록** — 집계 방법 · 이름 매핑 · 주의

숫자만 채우고 **서술(한 줄 평, 팀 제안)은 그 달 데이터에 맞게 다시 쓴다.** 매달 같은 문장을 복붙하면 리포트가 죽는다.

각 Part 끝에 `| 질문 | 답 |` 판정 표를 둔다. "부채가 해결되고 있나 / 효율적인가 / 균등한가 / 지속 가능한가"처럼 질문을 고정하면 달마다 답만 갈아 끼울 수 있다.

## 4. HTML 시각화 — 데이터와 렌더러를 분리한다

산출물은 **HTML 리포트**다. PPTX는 사용자가 파일로 달라고 할 때만 만든다(그때는 pptx 스킬을 읽는다).

### 4-1. 손으로 SVG를 쓰지 않는다

차트는 **생성 스크립트로 만든다.** 좌표·막대 폭·비율을 손으로 타이핑하면 반드시 틀린다.

```bash
cp -R ../YYYY-MM(직전 달)/gen ./gen        # 직전 달 아카이브 생성기를 그대로 가져온다
cp ${CLAUDE_SKILL_DIR}/assets/gen/*.py gen/  # tokens·charts는 번들 최신본으로 덮는다
#   gen/tokens.py       — 디자인 토큰 + CSS (라이트/다크 양쪽)
#   gen/charts.py       — 차트 함수 (표/표뷰 헬퍼 포함)
#   gen/build_report.py — 섹션 조립 → .html 출력 (아카이브에만 있다 — 실명·월별 서술이 들어 있어 번들에 넣지 않는다)
#   gen/dora_part.py    — Part 4 DORA 섹션 (아카이브에만)
```

- 데이터는 **상수 배열 하나**에만 둔다. 같은 수치를 두 곳에 쓰면 다음 달에 어긋난다
- 차트 함수는 `(라벨, 값)` 목록과 최대값만 받아 좌표를 계산한다
- 조립 스크립트를 다시 돌리면 같은 HTML이 나와야 한다

### 4-2. 차트를 그리기 전에 `dataviz` 스킬을 읽는다

필수다. 특히:

- **단일 계열 막대는 한 색**으로. 값에 따라 색을 진하게 하는 램프 금지
- **이중 축 금지.** 단위가 다르면 패널을 나누고 "패널 사이 기울기를 비교하면 안 된다"고 주석
- **범주 팔레트는 검증 스크립트를 돌린다.** 눈으로 판단하지 않는다. 라이트·다크 양 모드 모두
- 격자·축은 실선 헤어라인. 점선 금지
- 직접 라벨은 **선택적으로** — 끝점과 극단값만. 모든 점에 숫자를 붙이지 않는다
- 스택 세그먼트 사이 2px 간격. **`flex:0 1 pct%`로 축소를 허용한다** — `0 0`이면 간격만큼 컨테이너를 넘친다. 밝은 색 세그먼트의 라벨은 어두운 잉크로
- **차트마다 `표로 보기` 토글**을 단다. 색만으로 읽히는 값이 없어야 한다
- 히어로 숫자에는 `tabular-nums`를 쓰지 않는다 (표·축 눈금에만)
- **번호 목록에 CSS 그리드를 쓰지 않는다.** `<li>`를 `display:grid`로 만들면 중첩 `<ul>`이 번호 열로 밀려 섹션이 붕괴한다. 절대배치 마커 + padding으로 처리한다

### 4-3. 값의 폭이 크면 축을 바꾼다

선형 막대로 그리면 아래쪽 절반이 안 보이는 지표가 매달 나온다. 판단 기준:

- 작성 대비 리뷰 같은 **비율 지표는 쓰지 않는다** (§1)
- 축을 바꿨으면 캡션에 이유를 적는다 ("값의 폭이 42배라 로그 축")

### 4-4. 라이트·다크 양쪽 설계

토큰을 bare `:root`에 전부 선언하고, `@media (prefers-color-scheme: dark)`는 `:root:not([data-theme="light"])`로 가드, `:root[data-theme="dark"]`도 따로 재정의한다. `body`에 배경색을 명시한다. 한국어 본문에는 `word-break: keep-all`.

## 5. 차트 표준 세트 — 연속성이 목적

매달 **같은 차트**를 그린다. 형태를 바꾸면 전월과 눈으로 비교할 수 없다.

| # | 차트 | 형태 |
| --- | --- | --- |
| 1 | 개발자별 고유 작업 | 단일 계열 수평 막대 |
| 2 | 산출 집중도 추이 (상위 1인 / 3인) | 2계열 라인, 최근 4개월 |
| 3 | **월별 추이 스몰 멀티플** | 고유 작업 · Refactor · Changes Requested · 사람 vs 봇 리뷰 |
| 4 | 작업유형 프로필 | 개발자별 100% 스택 (8유형을 5그룹으로) |
| 5 | 리뷰 참여 순위 | 단일 계열 막대 (리뷰한 PR) |
| 6 | DORA 월별 추이 | 스몰 멀티플 — 테스트 동반률 · 개발 구간/리드타임 (시작월 기준) |
| 7 | 리뷰 외 기여 | 3패널 — 백포트 집중도 · 인프라·문서 · 봇 리뷰 |
| 8 | DORA 표 | 개인 전후(같은 repo) · 6~9월 현황 · repo별 (표로) |

**과거 월 데이터가 있으면 추이 차트에서 빼지 않는다.** 표만 남기고 그래프를 지우면 추세가 사라진다. 전월 값을 툴팁에 넣어 비교를 붙인다.

## 6. 회의 어젠다 md (선택)

"회의에서 나눌 자료", "어젠다", "논의 자료"를 요청하면 리포트와 별도로 만든다. 리포트는 진단, 어젠다는 **결정**이다.

안건마다 이 구조를 강제한다:

```
데이터 → 논점 → 선택지 A/B/C + 각각의 얻는 것·잃는 것 → 결정할 것 체크리스트 → 담당·기한 칸
```

- **선택지에는 권고안을 표시**하고 이유를 한 줄로
- **진행 시간·안건별 분 배분은 적지 않는다** (사용자 결정, 2026-09-28). 순서표는 순서와 내용만
- **이미 합의된 사항은 "새 제안"으로 올리지 않는다.** 전월 회의에서 방향이 나온 건이면 "이행 시점 확정"으로 프레이밍한다
- 맨 끝에 **액션 표**(액션 · 담당 · 기한 · 다음 달 검증 지표). 검증 지표가 없는 액션은 다음 달에 확인할 수 없다
- 맨 끝에 **이 자료의 한계** 섹션 (§7)

전월 리포트가 있으면 **전월 액션 추적표**도 만든다 — 전월에 개선됐다고 기록된 지표가 이번 달에 유지됐는지 대조한다.

## 7. 문체 — 의인화와 직역투 금지

이 리포트는 사람 평가에 쓰인다. 문장이 데이터보다 세면 안 된다.

### 금지 — 위반 시 롤백

- **과정 서술** — 재수집·재계산·정정·"지난 공유 수치와 다르다"·"X를 뺀 값이다"·제외 repo 경위. 리포트·어젠다·노션 어디에도 쓰지 않는다. **제거를 요청받은 문장을 설명 문장으로 바꿔 넣지 않는다** — 지운다
- **추상명사 의인화** — 추상명사를 주어로 세우고 극적 동사를 붙이는 습관. "분포는 무너졌다", "리뷰가 통과 절차로 작동한다", "부담이 전가된다", "차트가 같은 이야기를 한다", "지표가 되돌아갔다". 처방: 주어를 **사람·PR·repo**로 되돌리고 실제로 일어난 일을 쓴다
- **판정 헤드라인 + 숫자 나열** — 굵은 글씨로 결론을 선언하고 뒤에 동사 없는 숫자를 쌓는 형태. 세 개가 같은 모양으로 반복되면 근거가 판정을 장식하는 것처럼 읽힌다. 처방: 평서문으로, 비율 대신 원래 숫자로 ("36%" → "613건 중 221건")
- **은유 중첩** — "게이트를 씌운다", "부담을 절반 가른다", "278 PR을 받쳤다", "이 덩어리의 핵심"
- **직역투** — "~라는 수치는", "인과는 확정할 수 없다", "구분되지 않는다"(피동), "측정 가능한 형태로", "~로 취급", "파생된다"
- **데이터가 말해주지 않는 결론** — 리뷰 지표는 GitHub 이벤트만 센다. "리뷰에서 걸러지는 게 없다"고 단정할 수 없다

### 유지

격식(평어체/합니다체)은 원본 리포트를 따른다. 짧고 구체적인 표현(`빨간불`, `얇은 리뷰어 풀`)과 업계 용어(`트레이드오프`, `리드타임`, `DORA`, `bus factor`)는 남긴다.

윤문이 필요하면 `humanize-korean`을 먼저 돌리고 `humanize-me`를 마지막에 적용한다.

### 한계 섹션 (필수)

리포트와 어젠다 양쪽 끝에 넣는다:

- LOC는 규모 참고용 — 노력·품질의 지표가 아니다
- 리뷰 지표는 GitHub review 이벤트만 센다. 슬랙·페어링·구두 리뷰는 안 잡힌다
- 개인 산출 감소가 곧 기여 감소는 아니다 (repo 축소·역할 이동 효과)
- 기술부채는 Refactor 유형으로 한정한 정의다. 부채 티켓 체계가 없으면 유입량은 측정 못 한다
- 퇴사자의 부분월 데이터 (§10)

## 8. 검증 — 두 번 돈다

### 8-1. 수치 교차검증 (스크립트로)

"다 됐다"는 검증이 아니다. `${CLAUDE_SKILL_DIR}/scripts/verify_totals.py`를 작업 디렉토리로 복사해 FACTS를 채우고 돌린다:

- 개발자별 합 = 집계 대상 PR 수
- 고유 작업 + 백포트 + 봇 = 집계 대상
- 작업유형 분포 합 = 고유 작업 수, **스택 차트의 행별 합 = 각자 고유 작업**
- 리뷰 커버리지가 음수/100% 초과가 아닌가
- 차트의 막대 폭·좌표가 값/최대값과 일치하는가
- 본문에 인용한 모든 비율을 원래 숫자로 재계산

**내부 모순을 찾는다.** 요약의 서술과 상세 표가 어긋나는 일이 반복해서 생겼다("나머지 전원 감소"라고 썼는데 표에는 증가한 사람이 넷). 요약 문장의 주장은 전부 표와 대조한다. 모순을 찾으면 정확한 쪽으로 고치고 사용자에게 알린다.

### 8-2. 시각 QA (렌더해서 눈으로)

코드 리뷰만으로 HTML을 통과시키지 않는다. `python3 ${CLAUDE_SKILL_DIR}/scripts/visual_qa.py <파일.html>`을 돌린다 — 가로 스크롤, overflow 컨테이너 밖으로 넘치는 요소, **4,000px 초과 컨테이너**(그리드/플렉스 붕괴 신호)를 데스크톱·좁은 화면 양쪽에서 검사하고 라이트·다크 전체 페이지를 캡처한다.

**캡처는 차트뿐 아니라 모든 섹션을 한 장씩 본다.** 차트만 확인하고 넘어가면 목록·표 섹션의 붕괴를 놓친다. 위반은 폰트 축소로 때우지 않는다 — 라벨 위치를 옮기거나 항목을 줄인다. 고쳤으면 다시 돌린다.

렌더가 불가능한 환경이면 "시각 QA를 건너뛰었다"고 전달 시 알린다.

## 11. 집계 범위가 바뀌었을 때

repo가 편입·제외되면 총량이 전부 흔들린다. 이 순서로 처리한다.

1. **재계산 가능한 지표를 전부 다시 계산한다** — repo 표, 고유 작업, 집중도, repo별 분포, Refactor 비중과 0건 repo 수, 리뷰 없이 머지 비율, 봇 리뷰(repo별 내역이 있으면)
2. **repo별 분해가 불가능한 지표를 식별한다** — GitHub 리뷰 데이터에는 repo 정보가 없다. 개인별 리뷰 이벤트 · 작업유형 · 의미 LOC가 여기 해당한다. **추정하지 말고 이전 기준을 유지하고 해당 표·차트마다 기준을 표기한다**
3. **전월도 같은 기준으로 환산**해 추세를 만든다. 환산 근거를 남긴다 ("전월 해당 repo 고유 작업 28건을 뺀 값")
4. **추이 차트는 원 기준을 유지한다.** 오래된 달을 분해할 수 없으면 기준을 섞지 말고, 새 기준 값은 캡션에 병기한다
5. **산출이 전부 제외 repo에 있던 사람**은 산출 표에서 빠진다. 리뷰 기여는 유효하므로 "리뷰만" 쪽으로 옮기고 각주를 남긴다
6. 변경 경위는 리포트에 쓰지 않는다(§7). 부록 대상 repo 목록만 현재 기준으로 고치고, 경위는 아카이브 `published-baselines.md`에 남긴다

범위를 **소급 적용할지 다음 달부터 적용할지**는 사용자에게 확인한다. 작업량이 10배 차이 난다.
